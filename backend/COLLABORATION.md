# 백엔드 협업 지침

이 지침은 `backend/`를 작업하는 사람과 AI 에이전트에 적용한다. 작업별 API 명세와 공통 코드, 서로 다른 담당자의 구현을 연결할 때 따르는 절차를 담는다.

## 팀원 PC에서 설정하기

이 파일과 `RULEBOOKS/`는 저장소의 일반 Markdown 문서다. 에이전트의 자동 로딩 여부에 관계없이 작업을 시작할 때 직접 열도록 안내한다.

- 에이전트가 자동으로 읽는 로컬 지침 파일에 아래 문장을 넣는다. Codex를 저장소 루트에서 시작하는 팀원은 루트의 로컬 `AGENTS.md`에 넣는다. Claude Code를 사용하고 로컬 `CLAUDE.md`를 읽도록 설정했다면 그 파일에 넣는다. 기존 개인 지침이 있다면 아래 문장만 추가한다.
- 지침 파일을 자동으로 읽는지 확인하기 어렵다면 아래 문장을 작업 요청에 붙인다. 팀에서 공용 파일을 수정하면 해당 변경이 들어간 브랜치나 커밋을 반영한다.

> 백엔드 작업 전에 저장소 루트 기준 `backend/COLLABORATION.md`를 열고 그 지침을 따라줘. 대상 API ID와 계약 출처를 먼저 확인해줘.

## 0. 작업 범위에 맞는 저장소 문서를 읽는다

- 구현 전 [백엔드 README](README.md)와 [작업 규칙](../RULEBOOKS/contributing.md)을 읽는다. 작업의 구조·명명·검증에 해당하는 부분을 적용한다.
- PR과 머지가 관련되면 [머지 규칙](../RULEBOOKS/merge-rules.md)을, 실행이나 배포가 관련되면 [실행·배포 가이드](../RULEBOOKS/local-and-deploy.md)를 읽는다. 전체 흐름은 [팀 규칙 요약](../RULEBOOKS/RULE_SUMMARY.md)에서 확인한다.
- 에이전트는 코드 변경, 테스트, PR 본문 초안을 준비할 수 있다. Git 커밋은 팀 회의 결정에 따라 각 작업자가 직접 한다.

## 1. 작업에 사용할 기준을 확인한다

1. 작업 범위와 기준 브랜치를 확인한다. 보통 최신 `develop`을 기준으로 하고, 기존 기능을 수정할 때는 해당 API의 구현, 테스트, 실제 호출부를 먼저 찾는다.
2. 기능 명세의 `F-…`와 API 명세의 `API-…`를 구분한다. 기능 하나가 여러 API를 사용하면 이번 변경에 포함되는 API와 연결되는 API를 각각 적는다.
3. 작업 요청에 포함된 명세, 로컬 파일, 또는 읽을 수 있는 팀 이슈·PR에서 계약을 확인한다. Notion이나 GitHub 플러그인 없이도 적용할 수 있다. 링크에 접근할 수 없다면 작업자에게 구현에 필요한 부분을 채팅에 붙여넣거나 파일로 제공해 달라고 요청한다. 공개 이슈·PR에 옮길 때는 팀이 공개할 수 있는 내용과 가짜 예시를 사용한다.
4. 두 담당자 이상이 쓰는 계약은 **제공자와 호출자가 같은 기준을 참조**한다. 이미 합의된 위치가 있으면 그 링크와 해당 섹션을 남긴다. 문서가 수정될 수 있으면 버전·수정일·커밋 중 식별 가능한 값을 함께 기록하거나, 합의한 필드·타입·오류 예시를 관련 PR에 적는다. 기준을 변경하면 영향을 받는 담당자와 변경 범위를 맞추고 관련 PR의 참조도 갱신한다.
5. 기존 API 변경은 현재 호출자의 기대와 테스트를 확인한다. 코드, 명세, 회의 결정이 충돌하면 출처, 차이, 영향을 받는 호출자를 적는다. 작업 결과를 바꾸는 정보가 빠졌다면 질문을 좁혀 확인한다. 예를 들어 토큰 전달 방식이 미정이면 그 방식에 의존하는 인증 연결은 확인 뒤 적용하고, 공개 조회처럼 독립적인 작업은 이어간다.

### 호출자와 공유할 계약

작업에 해당하는 항목을 기존 이슈·PR이나 팀이 접근할 수 있는 명세에 남긴다. 링크만으로 팀원이 확인하기 어렵다면 공유 가능한 필드와 동작을 본문에도 적는다.

- API ID, HTTP 메서드, 경로, 호출자, 접근 조건, 인증 정보의 전달 위치.
- 입력 필드의 이름·타입·필수 여부·기본값, 응답 구조와 HTTP 상태, 호출자가 분기하는 오류 코드.
- ID와 상태 값의 가짜 예시, 시간 형식·시간대, 목록의 정렬·페이지 시작 값 또는 커서 형식.
- 생략, `null`, 빈 문자열, 빈 배열이 결과를 바꾸는 경우 각각의 의미. 예를 들어 첨부 목록 생략이 유지인지, 빈 배열이 전체 제거인지 명시한다.
- 성공 시 생기는 데이터 변경과 후속 작업, 재호출 시 결과, 다른 담당자의 API나 화면에 필요한 변경.

## 2. 담당 영역 사이의 경계를 맞춘다

아래는 기존 API 담당을 기준으로 한 협업 접점이다. 실제 담당자나 범위가 바뀌면 해당 작업의 이슈·PR에서 확인한다.

| 접점 | 함께 맞출 내용 |
| --- | --- |
| **A 모집·지원 ↔ B 인증·회원** | 최종 합격자 등록에서 사용할 회원 생성·초대 로직, 사용자 ID와 학번·기수의 타입, 기존 회원 처리, 등록 후 메일만 실패했을 때의 결과 |
| **B 인증·회원 ↔ A/C 보호 API** | 공통 인증 코드가 제공하는 사용자 ID·역할, 세션이 무효일 때의 응답, 운영진 접근 범위. 게시글·댓글의 작성자 검사처럼 기능에 종속된 권한은 해당 기능에서 확인 |
| **A 모집·일정 ↔ B 운영 콘텐츠** | 현재 공개할 모집 회차의 기준, 모집 회차·일정 ID의 매핑, 포스터와 일정이 참조할 원본 |
| **C 게시판·프로젝트 ↔ B 운영 대시보드** | 게시글·댓글 ID, 게시판 구분, 조회 가능한 상태, 링크가 가리키는 대상 |
| **A/B/C ↔ 파일·정리 작업** | 파일 연결 권한, 파일 ID와 저장 위치, 다운로드 조건, 원본과 첨부의 연결 해제 및 삭제 처리 |
| **백엔드 ↔ 프론트·AI·인프라** | 프론트가 실제로 보내고 읽는 필드, AI 요청·응답과 채점 실패 처리, 내부 호출 주체·권한, 환경 설정과 배포 순서 |

- 맡은 기능은 요청 처리부터 서비스·저장·테스트까지 같은 담당 영역에서 작업한다. 다른 영역의 기능을 호출할 때는 기존 서비스의 공개 진입점을 사용한다. 예를 들어 모집에서 회원을 등록할 때 회원 생성 규칙을 재사용하고, 해당 영역의 Repository에 직접 쓰지 않는다.
- 공통 코드나 공유 필드를 바꾸면 어떤 API·호출자·저장 데이터가 영향을 받는지 확인한다. 여러 PR이 같은 공통 코드에 의존하면 공통 변경의 담당자와 머지 순서를 정하고 각 PR에 선행 PR을 링크한다.
- 호출부가 새 형식을 쓰는 동안 기존 호출부도 동작해야 하는 경우, 호환 기간과 제거 시점을 합의한다. 호환이 깨지는 변경은 관련 호출부와 적용 순서를 함께 정한다.
- Git 충돌 없이도 두 PR이 같은 경로나 역할 규칙을 다르게 정의할 수 있다. 선행 PR이 머지되면 팀 작업 규칙에 따라 그 변경을 반영하고, 제공자와 호출자를 연결한 상태에서 동일한 예시로 확인한다. 공통 코드가 준비되기 전에 독립적으로 작업했다면 이때 임시 연결을 실제 연결로 교체한다.

## 3. 백엔드 구조와 HTTP 계약을 유지한다

- [백엔드 코드 구조](README.md#코드-작성-규칙)에 맞춰 `controller → service → repository`로 연결한다. Controller는 요청·형식 검사·응답을 처리하고, Service는 업무 규칙을 적용하며, Repository는 저장소 접근을 맡는다. Service에 `HttpServletRequest` 같은 웹 계층 객체를 넘기지 않는다.
- 사용 가능한 공통 인증, 응답, 예외 처리 코드가 작업 브랜치에 있는지 확인하고 재사용한다. 아직 합쳐지지 않은 코드는 관련 PR을 명시한다. 같은 목적의 응답 래퍼, 예외 처리기, 인증 구현을 각 기능에서 따로 만들지 않는다.
- 성공 응답의 포장 방식과 필드명, 오류의 HTTP 상태·`code`·`message`는 호출자가 처리하는 계약이다. 합의된 공통 오류 코드를 재사용하고, 호출자가 별도로 처리할 업무 오류는 해당 영역에서 정의한다. 명세와 구현에서 같은 오류에 다른 이름을 쓰고 있다면 적용할 이름과 변경 범위를 관련 담당자와 확인한다.
- HTTP 메서드와 경로의 조합이 기존 API와 겹치는지 확인한다. 공개·회원·관리자·내부 요청의 경로와 권한은 API별 계약을 따르고, 클라이언트와 서버가 같은 경로를 사용하도록 확인한다.
- 요청 DTO, 저장 모델, 응답 DTO는 각 경계에서 필요한 필드를 다룬다. 저장된 객체를 응답으로 그대로 내보내면 내부 필드가 노출되거나 저장 구조 변경이 API에 전파될 수 있으므로 반환 필드를 명시한다.
- 같은 자원을 가리키는 ID의 타입과 값은 조회·수정·삭제에서 호환되어야 한다. 내부 저장 이름과 API 이름이 다르면 변환 지점을 한 곳에 둔다. 정렬 결과가 같은 항목이 여러 개라면 페이지 사이의 순서를 재현할 수 있도록 보조 정렬 기준을 확인한다.

## 4. 인증·권한·개인정보를 보호한다

- 보호 API는 서버가 검증한 인증 정보에서 사용자 ID와 권한을 얻는다. 요청 본문의 사용자 ID·역할이나 화면에서 버튼을 숨긴 상태를 권한 근거로 쓰지 않는다.
- 역할 검사와 대상별 권한을 함께 확인한다. 예를 들어 회원의 게시글 수정은 해당 글의 작성자 여부를, 첨부 다운로드는 연결된 원본을 읽을 수 있는지 확인한다. 공개 목록과 공개 상세에서 비공개·삭제 대상의 노출 기준을 함께 맞춘다.
- 로그인 토큰의 발급자, 헤더·쿠키 전달 방식, 운영진의 작업 범위는 실제로 합의한 계약을 적용한다. 문서가 엇갈릴 때 별도의 역할·예외·토큰 방식을 추정해서 추가하지 않는다. 로그아웃, 비활성화, 역할 변경처럼 세션을 무효화하는 작업은 해당 세션으로 후속 요청이 어떻게 처리되는지 확인한다.
- 예약 작업, 작업 대기열, AI 호출의 인증은 사용자 로그인과 구분한다. 내부 경로에서도 허용된 서비스의 호출인지 검증하고, 필요한 실행 권한만 부여한다. 쿠키 기반 요청을 변경하는 작업은 실제 프론트 주소에서 쿠키 전송과 교차 출처 요청 보호가 기대대로 작동하는지 확인한다.
- 개인정보·비밀값 취급은 [공개 저장소 규칙](../RULEBOOKS/contributing.md#5-공개-레포에서-지킬-것)을 따른다. 실제 회원·지원자 정보, 토큰·쿠키 원문, 키, 채점 루브릭을 코드·테스트·로그·공개 PR 등에 남기지 않는다. API 응답과 AI 요청에는 해당 기능에 필요한 항목만 포함한다. 환경별 설정에는 각 환경의 자원과 자격 증명을 사용한다.

## 5. 저장 구조와 비동기 작업의 일관성을 확인한다

- 실제로 사용할 컬렉션·문서 경로, ID, 필드 타입·기본값, 상태와 조회 조건을 관련 작업에서 확인한다. 영역을 넘는 참조는 값을 만드는 쪽과 읽는 쪽이 같은 ID·타입을 사용하도록 맞춘다. 이름처럼 복사해서 저장하는 값은 원본 변경·삭제 시 표시 기준을 정한다.
- 여러 기능이 한 상태를 읽거나 바꾸면 허용되는 상태 전이, 전이를 수행하는 작업, 각 상태에서 화면에 표시할 결과를 함께 확인한다. 모집 마감, 채점 완료, 계정 비활성화 등은 변경 직후와 재처리 이후의 결과도 대조한다.
- 기존 문서에 필드가 없는 경우와 새 코드가 쓰는 형식을 함께 확인한다. 구조를 바꾸는 작업은 기존 데이터 읽기와 변환 방법, 변경 적용 순서를 PR에 적는다. Firestore 조회 조건을 추가할 때는 [인프라 README](../infra/README.md)의 인덱스 규칙을 확인하고 필요한 설정 변경과 적용 순서를 공유한다.
- 학번 중복 방지, 초대 링크 1회 사용, 일괄 상태 변경처럼 동시에 요청이 들어오는 작업은 검사와 저장 사이에 다른 요청이 끼어도 규칙이 유지되도록 설계한다. 여러 DB 변경이 한 결과를 이루면 트랜잭션이나 일괄 쓰기를 선택하고, 전체 실패와 부분 성공 중 어떤 계약인지 맞춘다.
- DB 저장과 메일·파일 저장소·작업 대기열 호출이 이어지면 각각이 실패했을 때 남는 상태와 재시도 동작을 확인한다. 예를 들어 회원 저장 후 초대 메일만 실패하면 회원 등록의 성공 여부와 재발송 방법을 명세에 맞춰 처리한다. 외부 호출이 트랜잭션 재시도마다 실행되지 않도록 호출 위치를 확인한다.
- 스케줄러·큐 호출은 같은 작업이 재전달될 수 있다. 작업 ID와 상태를 기준으로 재시도·중복 호출 시 결과가 일관되게 하고, 의도적인 재발송·재실행과 자동 재시도를 구분한다.
- 삭제·비활성화·공개 상태를 바꾸는 기능은 원본 조회 외에 목록·상세·첨부·대시보드 등 같은 데이터를 읽는 곳에서 결과를 확인한다. 첨부 연결·삭제가 정리 작업과 겹칠 수 있다면, 연결된 파일이 정리 대상으로 남지 않는지 확인한다.

## 6. 검증 결과를 다음 담당자가 이어받을 수 있게 남긴다

변경에 해당하는 시나리오를 골라 확인하고, 현재 브랜치의 [실행 안내](README.md)에 있는 명령을 사용한다. 환경이나 접근 권한이 없어 실행할 수 없는 항목은 실행 여부와 필요한 확인을 PR에 적는다.

| 변경 | 확인할 시나리오 |
| --- | --- |
| API 요청·응답 | 정상 예시와 잘못된 입력, 실제 HTTP 상태·JSON 필드·오류 코드, 기존 호출부가 기대하는 응답 |
| 인증·권한 | 인증 없음·만료, 권한 부족, 대상 소유권, 정상 권한. 세션 무효화가 포함되면 이후 요청 |
| DB·목록 | 기존 데이터의 누락 필드, ID 타입, 정렬·페이지 경계, 해당되는 인덱스 및 동시 요청 |
| 메일·파일·예약·AI | 중복 실행, 일부 단계 실패 후 재시도, 재실행 시 남는 데이터나 외부 효과 |
| 담당 영역 간 연결 | 제공자와 호출자가 같은 입력·기대 결과를 사용한다. 예를 들어 합격자 등록은 회원 서비스와 연결해 신규 회원, 기존 회원, 초대 메일만 실패한 경우를 확인한다. 각자 만든 목으로만 확인한 경우 PR에 실제 연결 검증이 남아 있다고 적는다. |

기존 [PR 템플릿](../.github/pull_request_template.md)에 관련 기능·API ID, 변경된 계약이나 공유 데이터, 선행 PR, 실행한 테스트와 결과를 적는다. 환경 설정·인덱스처럼 순서가 필요한 변경은 적용 순서도 적는다. 테스트와 리뷰는 팀의 기존 절차를 따른다.

계약 변경을 다른 담당자가 이어받아야 할 때는 PR 본문에 아래 항목을 사용한다. 변경이 있는 항목만 채운다.

```text
대상 API와 호출자
합의한 계약의 출처와 버전
이전 동작과 새 동작
함께 변경할 API·공유 필드·설정
선행 PR과 머지·적용 순서
실행한 검증과 아직 확인할 항목
```
